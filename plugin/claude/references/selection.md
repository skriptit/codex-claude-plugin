# Native user selections

Use this contract whenever decision coordination or review reaches a user checkpoint, including resumed runs. Present the complete recommendation in the main conversation first. Put the exact proposal or agreed finding IDs, concrete fixes, evidence and scope there; the menu only names the choice about that immediately preceding recommendation.

1. Resolve a callable native selection tool before falling back to chat. Prefer the directly listed `request_user_input_async`; inspect the main task's actual tool list and schema, since a forwarding child may expose different tools. Only if absent, use tool discovery when the host provides it. Use another native selection tool only if its actual instructions permit this kind of decision in the current mode. A Plan-only tool is unavailable outside Plan mode, and a tool restricted to optional clarification cannot collect required approval. Skill instructions never override those restrictions.
2. Call the permitted tool in the main task with one question and the two options specified by the invoking workflow. The examples use the native async schema `{questions: [{title, options}]}`, where `options` contains plain strings. Use the actual available schema: keep the title or question one short sentence, each option label at most five words, and any supported header at most 12 characters. If another permitted tool requires descriptions, use one short sentence each. Use the supplied title and labels verbatim. Reference the recommendation already shown in the session; never paste findings, file lists, the full proposal or command text into the question, title, labels or descriptions.
3. Wait for the actual response using that tool's documented response or continuation mechanism. For an asynchronous request, retain its request identity and wait for its matching answer; creating the request is not receiving an answer. Keep the choice pending through a timeout or missing answer. A preselected option, dismissal or elapsed time is not authorization. Accept an unambiguous user text reply as well, including a narrower fix scope; clarify an ambiguous reply before dependent work.
4. A required selection is complete only when the user has answered it or an explicit answer for the same unchanged recommendation already exists. Do not finish an agreed or stopped decision, or a review with accepted findings, with only a summary and silently omit its menu. If inspection of the main task's tools and any available discovery confirms that no permitted native selection tool is available, explain that exact host limitation and ask the same short question in plain text. Never simulate clickable options or claim a menu was displayed when no tool produced one.

After the actual answer, apply the invoking workflow's next step immediately. For a decision's **Approve** or **Accept**, continue into implementation or execution under [decision coordination](decide.md); for a review's fix choice, apply its selected fixes. Preserve explicit human limits and the selected scope. Keep an unanswered approval pending; an optional-question default does not authorize implementation.
